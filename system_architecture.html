System Architecture Specification

Research Specification | Multi-Sensor GNSS-INS Fusion & Dead Reckoning Engine
1. Executive Summary & Core Objective

This document outlines the software and hardware architecture for a high-precision, low-latency Inertial Navigation System (INS) integrated with vehicle telematics. The objective is to restrict positional drift to < 10% of total distance traveled (target: < 0.5% - 1% with car sensors) during GNSS blackouts (tunnels, underground metros, basements) across smartphone (10Hz) and Edge-based (200Hz) execution tiers.

3. Dual-Tier Technology Stack

Tier 1: Smartphone Mobile Application (10Hz)

  • Frontend UI: Flutter (Dart) / Native Android (Kotlin)
  • Native Core: C++ via JNI for high-performance math
  • Hardware Processing: SensorHub FIFO batching API
  • Connectivity: Bluetooth LE (ELM327) + Android Auto API
  • Database: SQLite + SpatiaLite (Offline tunnel polylines)

Tier 2: Edge Simulator & Node (200Hz)

  • Runtime Platform: Embedded Linux (Jetson / RPi) / C++20
  • Framework: ROS2 (Robot Operating System) Nodes
  • Math & Fusion Engine: Eigen3 (Linear Algebra) + Sophus
  • Perception Fusion: OpenCV (Visual Odometry)
  • Telemetry Dashboard: Python PyQt6 / WebSockets + Plotly
4. Algorithmic Pipeline & Mathematics
1. DYNAMIC FRAME ALIGNMENT (Direction Cosine Matrix): A_vehicle = R_alignment * A_phone - Static: Resolves Pitch & Roll by aligning IMU Z-axis with Earth Gravity Vector. - Dynamic: Solves Yaw by matching linear drive pulse with GNSS vector before entry. 2. ERROR-STATE EXTENDED KALMAN FILTER (15-State ES-EKF): State = [Position_Error, Velocity_Error, Attitude_Error, Accel_Bias, Gyro_Bias] 3. DRIFT CONSTRAINTS (Circuit Breakers): - Zero Velocity Update (ZUPT): Forces Velocity = 0 when Gyro & Accel variance < Threshold. - Non-Holonomic Constraints (NHC): Enforces V_lateral = 0 and V_vertical = 0. - HMM Map Matching: Snaps trajectory to 1D center-line polylines inside mapped tunnels.
